    ローカルAPIとPython・TypeScript SDK¶

    日本語 | English

    • 利用可能：v0.0.4。公開レジストリには未配布です。
    • 同じLinuxホストから、ワーカーの作成・起動・実行・照会・回収を行います。
    • SDK → oaiso api stdioの専用パイプ → 公開Go API → 既存nodeのUnix socket、の順に呼び出します。
    • TCPの待受・管理socketのnetwork公開は追加しません。呼び出し元には既存socketへの権限が必要です。任意のhost mountなどを指定できるため、信頼したプロセスだけで使います。

    前提と対応範囲¶

    項目 条件
    ホスト 実行基盤と認証Proxyを準備済み。ワーカーイメージはビルド・import済み
    版 CLI・node・Proxyを対応するビルドで配置。ローカルAPIはv1、nodeはv2
    Python 3.12以降。SDK実行時の追加依存なし。uvの導入
    TypeScript Node.js 22以降。SDK実行時の追加依存なし。Node.jsの導入。コンパイラ・Node型は開発時だけ使用
    設定 openへ明示。CLIの設定ファイル・認証profileは自動で読み込まない
    認証 Proxy管理secretを既存の0600ファイルから読み、Options.ProxyAdminSecretへ渡す。実APIキー・OAuthは認証Proxyに保持
    作業ファイル ProjectDirは実在する絶対パス。通常の/workspace共有と同じ影響がある
    対応操作 create・launch・start・exec・get・list・wait・stop・remove・request・remove_request・quarantine・資源とcapabilityの照会。加えてfiles・jobs・checkpoint
    Go APIで行う操作 PTY・入出力stream・image build・成果物tar・プレビュー・通信規則の即時変更・checkpointの保持管理・StoreやケースProxyの作成など
    • 一般通信はGo APIと同じく既定拒否。許可を追加する場合はOptions.EgressPolicyを設定します。
    • 作業ファイルへ書き込む場合は、所有者に合う数値UID/GIDをLaunchRequest.Userへ指定します。省略時はイメージのユーザーを使用し、SDKは所有者を変更しません。
    • 実行用の仮トークンや、ホストの実資格情報を返すAPIは追加しません。
    • SDKの内部stdoutはプロトコル専用。ゲストのstdout・stderrはexecの戻り値で明示的に受け取ります。利用者が実行したコマンド自身の出力は、利用者側で管理してください。

    Pythonを導入する¶

    • 通常ユーザーで、取得済みのこの機能を含むソースのルートから実行。
    • 仮想環境を新規作成します。既存環境がある場合は別の場所を選びます。
    uv venv --python 3.12 .venv-sdk
uv pip install --python .venv-sdk/bin/python ./sdk/python
.venv-sdk/bin/python -c 'from oaiso import Client; print("SDK import OK")'
    • 成功の目印：SDK import OK。nodeへの接続確認は次の例で行います。

    作成・実行・回収¶

    • oaisoをPATHへ配置済み。以下をexample.pyとして保存します。
    • /srv/work/projectは実在する作業ディレクトリへ置換します。管理secretのパスは配置に合わせます。
    • 要求IDは例です。新しい作業には別のIDを使い、同じ作業の再送では変えません。
    from pathlib import Path
import os
from oaiso import Client

secret = (Path.home() / ".config/codex-dock/proxy-admin-secret").read_text().strip()
request = {
    "RequestID": "my-app/project-1/task-1/attempt-1",
    "ProjectDir": "/srv/work/project",
    "Image": "codex-dock:latest",
    "Profile": "compact",
    "User": f"{os.getuid()}:{os.getgid()}",
    "NoInternet": True,
}

with Client({"ProxyAdminSecret": secret}) as client:
    worker = client.create(request)
    try:
        client.start(worker["ID"])
        result = client.exec(worker["ID"], ["printf", "hello"])
        print(result["exit_code"], result["stdout"].decode())
    finally:
        client.remove_request(request["RequestID"], force=True)

    .venv-sdk/bin/python example.py

    出力例：

    0 hello
    • Client(...)は接続と版照合だけを行います。
    • createは起動前の資源を確保します。ゲストのコードはstartで開始します。
    • withの終了は接続を閉じる操作です。VMの停止・回収はstop・remove_requestを使います。

    TypeScriptを導入する¶

    • 通常ユーザーで、この機能を含むソースのルートから実行。
    npm --prefix sdk/typescript ci --ignore-scripts --no-audit --no-fund
npm --prefix sdk/typescript run build
    • アプリのディレクトリへ移動し、ソースの絶対パスを置換して実行。
    npm install /absolute/path/to/sandbox-oasis/sdk/typescript

    作成・実行・回収¶

    • 以下をアプリ側のexample.mjsへ保存します。TypeScriptでも同じAPIを使え、型定義を読み込めます。
    • 作業ディレクトリ・管理secret・要求IDの条件はPythonの例と同じです。
    import { readFile } from 'node:fs/promises';
import { homedir } from 'node:os';
import { Client } from '@oaiso/local';

const secret = (await readFile(`${homedir()}/.config/codex-dock/proxy-admin-secret`, 'utf8')).trim();
const request = {
  RequestID: 'my-app/project-1/task-2/attempt-1',
  ProjectDir: '/srv/work/project',
  Image: 'codex-dock:latest',
  Profile: 'compact',
  User: `${process.getuid()}:${process.getgid()}`,
  NoInternet: true,
};
const client = await Client.open({ ProxyAdminSecret: secret });
try {
  const worker = await client.create(request);
  try {
    await client.start(worker.ID);
    const result = await client.exec(worker.ID, ['printf', 'hello']);
    console.log(result.exit_code, result.stdout.toString());
  } finally {
    await client.removeRequest(request.RequestID, true);
  }
} finally {
  await client.close();
}

    node example.mjs
    • 出力例は0 hello。認証情報をconsole.logや起動引数へ渡しません。
    • TypeScriptの数値は安全な整数の範囲で指定します。非有限値・小数・安全範囲外の整数は送信前に拒否し、受信時も丸めた値を返しません。大きな64 bit整数を必要とする場合はGoまたはPythonを使います。

    取消・タイムアウト¶

    操作 取消の意味
    wait 待機のみを中断。VMは継続
    exec 実行中のゲストコマンドへ取消を伝える。完了や切断との競合では結果照合が必要
    create / launch Go APIの取消・回収処理を呼ぶ。要求IDを照会し、残る資源を回収
    stop / remove 応答がない場合、停止・回収の完了は未確認。get・requestで照合
    cancelのaccepted: true 対象callの取消を受け付けた。停止・回収の完了を示す値ではない
    接続切断・close 処理中のcallを取消し、接続を閉じる。作成済みVMの回収完了は保証しない
    • Python：pending = client.submit("wait", {"worker_id": worker_id})、pending.cancel().result()、pending.result()。
    • TypeScript：const pending = client.submit('wait', {worker_id: workerID})、await pending.cancel()、await pending.result。
    • TypeScriptは各操作の末尾のoptionsで{signal: controller.signal}も指定できます。
    • サーバー側の期限は既定180秒、最大1,200秒。Pythonはtimeout_ms、TypeScriptはtimeoutMsで指定します。0は既定値を使用。
    • Pythonのresult(timeout=秒)が時間切れになると取消を要求します。既に成功していた可能性があるため、変更操作では結果を照合します。
    • stopの停止猶予は別の秒数です。省略時10秒、0は強制停止。nodeへの通信期限とは異なります。

    再送とエラー¶

    値・状態 対応
    callのid 一つの接続内の応答照合番号。1から増加。SDKが付与
    LaunchRequest.RequestID node全体で永続する作成要求ID。1〜256 UTF-8 byte。組み込み元が付与
    pending / in_progress 処理中・復旧待ち。同じ要求IDで照会。別IDで重複作成しない
    complete 台帳上で作成が確定。現在の稼働状態はgetで照会
    failed 前回の作成が失敗。同じ不変設定・要求IDで再試行
    cleanup-pending / cleanup_pending 回収が未完了。ワーカーID・要求IDから回収を再試行
    conflict 同じ要求IDの不変設定が違う。元の設定を確認
    request_gone 完了済み要求のワーカーは削除済み。同じIDでは再作成しない
    outcome_unknown / transport_lost 結果が不明。request・getで照合してから判断
    version_mismatch 対応するCLI・node・Proxyを配置して接続し直す
    permission_denied 既存socket・ファイル権限を管理者に確認。SDKが権限を増やすことはない
    internal Go APIの未分類エラー。詳細文字列は秘匿。信頼したホスト側で状態・監査を確認
    • 自動再送はしません。作成の再送は同じ要求ID・同じ設定・同じ接続Optionsで行います。
    • createとlaunchの間で同じ要求IDを使い回すと競合です。
    • execは再送で二重実行する可能性があります。応答消失後に自動実行し直さないでください。
    • PythonのAPIErrorはcode・codes・requires_reconciliation・partial_result、TypeScriptはcode・codes・requiresReconciliation・partialResultを提供します。
    • エラーに含まれるWorker.IDは回収に使えます。エラー文字列には元の資格情報・引数・下位エラーを含めません。
    • requires_reconciliationは状態の照合が必要という意味です。falseでも、別のcallで作ったVMの停止を保証する値ではありません。
    • ワーカーのStatusは観測値です。未知の文字列を「停止済み」とみなしません。

    機械可読な仕様¶

    項目 定義
    接続・版 private pipeのNDJSON、ローカルAPI v1。改行ごとにJSON objectを1つ送信
    要求 version・id・method・params、任意のtimeout_ms
    応答 version・idと、resultまたはerror。エラー時に部分結果を併記する場合がある
    型 Options・LaunchRequest・WorkerなどはGo DTOのJSON名を維持。RequestIDとrequest_idなどの綴りは仕様を参照
    バイト列・時間 入出力はbase64。Go DTOのdurationはナノ秒、call期限はミリ秒、stop猶予は秒
    上限 要求1 MiB、応答4 MiB、exec出力はstdout・stderr各256 KiB、同時処理16 call。取消は枠外で受付
    超過 出力超過は処理を取消し、output_limitと部分出力を返す。大量出力・PTY・継続streamはGo APIを使用
    JSON検査 未知フィールド・重複キー・不正なframeを拒否。不正な外側frameでは接続を終了し、処理中の変更は照合が必要
    保存・再生成 JSON Schema。Go DTOから生成し、CIで差分を検出 
    oaiso api schema > local-api-v1.schema.json
    • このコマンドはnodeや認証へ接続しません。JSON Schemaはdraft 2020-12です。
    • x-oaisoに操作ごとの再送・取消、要求状態、結果型の対応を収録します。
    • Schemaは型とwire契約を定義します。資源予約・通信とモデルの権限・パス制約は、実行時にGo APIとnodeが検査します。
    • 互換性を壊す変更では新しいローカルAPI版と仕様を用意します。追加操作はcapabilities.methodsで確認します。
    • Go APIをすべてJSON化したものではありません。capabilityにない操作は使用しません。
    • 内部node HTTP APIをSDKから直接呼ばないため、内部DTOの変更と公開契約を分けて管理できます。

    ファイル・ジョブ・checkpointを操作する¶

    • 利用可能：v0.0.4。ローカルAPI v1への追加操作です。
    • clientは上の例で開いた接続、worker_idは起動中のワーカーIDです。
    操作 Python TypeScript
    ファイルを読む read_file(worker_id, "result.json") readFile(workerID, "result.json")
    書く write_file(worker_id, "input.json", data) writeFile(workerID, "input.json", data)
    一覧 list_files(worker_id, ".") listFiles(workerID, ".")
    background実行 start_job(worker_id, argv) startJob(workerID, argv)
    ジョブの照会・一覧 job()・list_jobs() job()・listJobs()
    ログを読む job_logs(worker_id, job_id, offset=0) jobLogs(workerID, jobID, 0)
    終了待ち・停止 wait_job()・kill_job() waitJob()・killJob()
    disk保存・一覧 checkpoint()・checkpoints() checkpoint()・checkpoints()
    保存内容の確認・削除 inspect_checkpoint()・remove_checkpoint() inspectCheckpoint()・removeCheckpoint()
    新規VMへ復元 restore_checkpoint(id, request) restoreCheckpoint(id, request)

    Pythonの操作例：既存のwith Client(...) as client:内で実行します。

    worker_id = worker["ID"]
client.write_file(worker_id, "input.json", b'{"task":"example"}')
print(client.list_files(worker_id))
job = client.start_job(worker_id, ["python3", "-c", "print('done')"])
finished = client.wait_job(worker_id, job["id"])
logs = client.job_logs(worker_id, job["id"], offset=0)
print(finished["exit_code"], logs["output"])

    TypeScriptの同じ操作：既存の接続とワーカーを使います。

    await client.writeFile(worker.ID, "input.json", Buffer.from('{"task":"example"}'));
console.log(await client.listFiles(worker.ID));
const job = await client.startJob(worker.ID, ["python3", "-c", "print('done')"]);
const finished = await client.waitJob(worker.ID, job.id);
const logs = await client.jobLogs(worker.ID, job.id, 0);
console.log(finished.exit_code, logs.output);
    条件 動作
    ファイル /workspaceからの相対パス。symlinkをたどらない。1回512KiBまで。Go API／CLIの64MiB上限とは別
    大きなファイル Go API／CLIを使う。SDKによる分割アップロードは未提供
    ジョブの起動 自動再送しない。応答消失時は一覧・返された部分IDで照会
    ログ nextを次のoffsetに使う。truncatedなら保持範囲の欠損あり
    終了待ちの取消 待機だけを中止し、ジョブを停止しない
    checkpoint 停止済みKataを保存。作成応答が消えた場合は一覧を照会してから判断
    復元 新しいRequestIDを指定。イメージ・digestの矛盾とrunc指定を拒否
    • checkpointの保存対象・制限も確認してください。RAMや接続は保存しません。
