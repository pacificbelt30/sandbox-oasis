    WSL2で実行ノードを準備する¶

    日本語 | English

    Ubuntu 24.04の自動判定とWSL向け事前確認は未リリース（main）です。公開版v0.0.8の自動配置はUbuntu 26.04のみ対象です。24.04では対応するソースからビルドします。

    対象はWindows 11上のWSL2・Linux x86_64です。Ubuntuの版だけではKataの実行可否は決まりません。実WSLでの導入・再起動・VPN接続は未検証です。検証範囲と、次の条件を確認してください。

    確認対象 必要条件・対処
    仮想化 Windows/UEFIで仮想化を有効化し、WSL2へnested virtualizationを公開。/dev/kvmの存在に加え、rootでVM作成が成功すること
    WSLカーネル kvm_intelまたはkvm_amd、vhost_vsock、vhost_net、tun、XFS/project quota。Ubuntuのgenericカーネル用モジュールでは代用不可
    systemd・cgroup systemdを有効化し、cgroup v2のcpu memory pidsを使用
    rootfs保存先 /var/lib/codex-dock-containerdに専用XFSをprjquota付きでmount。既定のext4や/mnt/cは使用不可
    プロジェクト まずWSLの/home配下を使用。Windows共有領域は所有者・権限・大文字小文字・監視性能の差に注意
    メモリ・容量 WSLに8 GiB以上を割り当て、Windowsにも余裕を残す。以下の例は32 GiBを事前確保。WSL内とWindows側の両方に空きが必要
    通信 WSL内から名前解決とHTTPSが成功すること。VPN・Hyper-V firewall・企業proxyの条件も確認
    停止・再起動 systemdサービスだけでWSLの常駐は保証されない。wsl --shutdown・Windows再起動の前にVMを停止し、再開後にmountとruntimeを再確認

    MicrosoftのWSL設定、systemd、ファイルシステム、通信を参照してください。Microsoftの6.6系・6.18系の設定にはKVM/vhostとXFS quotaがありますが、手元のカーネル・モジュール・CPUでの利用可否は別に確認します。

    1. Windows側を確認する¶

    WindowsのPowerShellで実行します。ディストリビューション名はwsl --list --verboseの表示に合わせてください。

    wsl --version
wsl --list --verbose
    • 対象ディストリビューションのVERSIONが2であることを確認します。Windows on ARMは現在の固定Dragonballプロファイルの対象外です。
    • WSLが古い場合は、作業を保存してからWindows側でwsl --updateを実行します。CPUやWindowsの制約でKVMが使えない場合は、対応する別のLinux/KVMノードを使用します。
    • %UserProfile%\.wslconfigを編集する場合は、既存設定を保ち、[wsl2]のnestedVirtualization=trueとメモリ上限を確認します。nested virtualizationの既定値はtrueです。WSL全体に適用されるため、他のディストリビューションの使用量も見積もってください。

    WSL内の/etc/wsl.confは既存項目を保ち、次を設定します。[boot]がある場合はそこへ追加します。

    [boot]
systemd=true

    設定の反映にはWSLの停止と再起動が必要です。wsl --shutdownは全ディストリビューションを停止します。稼働中のOaiso VMや他の作業を保存・停止した後だけ、PowerShellで実行します。

    wsl --shutdown
wsl --distribution Ubuntu-24.04

    2. WSL内の必須機能を確認する¶

    未リリース（main）のsetupは、適用時と次回起動用にvhost_vsock・vhost_net・tunを準備します。以下は導入前の確認・手動復旧用です。WSL内のUbuntuのシェルで実行します。kmodがなければ、先にsudo apt-get install -y kmodで導入します。

    uname -r
systemctl is-system-running
cat /sys/fs/cgroup/cgroup.controllers
sudo modprobe vhost_vsock
sudo modprobe vhost_net
sudo modprobe tun
ls -l /dev/kvm /dev/vhost-vsock /dev/vhost-net /dev/net/tun
    • systemdはrunningを確認します。degradedの場合はsystemctl --failedで失敗したunitを調べます。cgroupにはcpu memory pidsが必要です。
    • /dev/kvmがなければ、CPUに合う方だけを実行します。Intelはsudo modprobe kvm_intel、AMDはsudo modprobe kvm_amdです。
    • 手動のCPUモジュール読込が必要だった場合は、sudoedit /etc/modules-load.d/oaiso-wsl-kvm.confで実際に成功したモジュール名だけを保存します。既存の項目は保ち、IntelとAMDの両方を追加しないでください。再起動後も/dev/kvmを確認します。
    • Module ... not foundの場合はuname -rと/lib/modules/$(uname -r)を照合し、WSLを更新します。カスタムカーネルなら、同じビルドのkernel/modules VHDを.wslconfigへ指定します。mknodでデバイス名だけを作っても仮想化機能は追加されません。
    • setupのroot実行時にはKVM APIで空のVMを作成し、すぐに解放します。vCPU・guestメモリは確保せず、既存VMには触れません。成功しても、実際のKata起動の確認は別に必要です。

    3. 新規の専用XFSを準備する¶

    既存ノードの移行は保管・復元手順を先に実施します。以下は新規導入だけの例です。WSLのLinuxファイルシステム内に専用の32 GiBファイルを作り、loopデバイス経由でXFSとして使います。既存のext4.vhdxやWindowsのディスクをformatしません。

    WSL内で空きを確認します。Windows側でも、ディストリビューションのVHDが置かれたドライブに32 GiB以上と運用上の余裕があることを確認してください。

    df -h /var/lib
sudo apt-get install -y xfsprogs util-linux

    次のブロックは、保存用ディレクトリが存在する場合、対象ディレクトリが空でない場合、既にmount済みの場合に停止します。途中失敗時は、作成したファイルと空き容量を確認し、既存データを消して再実行しないでください。

    sudo bash -euo pipefail <<'SH'
image=/var/lib/oaiso-wsl/rootfs.xfs
target=/var/lib/codex-dock-containerd
test ! -e /var/lib/oaiso-wsl
test ! -L /var/lib/oaiso-wsl
install -d -o root -g root -m 0700 /var/lib/oaiso-wsl
test ! -e "$image"
test ! -L "$image"
test ! -L "$target"
mkdir -p "$target"
if mountpoint -q "$target" || test -n "$(find "$target" -mindepth 1 -print -quit)"; then
    echo 'Storage target is mounted or not empty; preserve it and use the migration guide.' >&2
    exit 1
fi
(umask 077; set -C; : > "$image")
fallocate -l 32G "$image"
mkfs.xfs "$image"
SH

    sudoedit /etc/fstabで既存行を保ち、次の行を一度だけ追加します。[automount] mountFsTab=falseを設定している場合は、WSL起動時にもこのmountが準備されるよう運用を調整してください。

    /var/lib/oaiso-wsl/rootfs.xfs /var/lib/codex-dock-containerd xfs loop,prjquota,nofail 0 0

    WSL内でmountし、FSTYPE=xfsとprjquotaまたはpquotaを確認します。

    sudo mount /var/lib/codex-dock-containerd
findmnt --mountpoint /var/lib/codex-dock-containerd -o TARGET,SOURCE,FSTYPE,OPTIONS

    containerdのunitはRequiresMountsForでこのmountを待ちます。XFSやquotaの確認に失敗する場合は配置へ進まず、mountを修正します。setupはファイル作成・format・fstab編集を自動実行しません。

    4. 配置と実動作を確認する¶

    ソースからの配置または対応版のバンドルで、計画を確認して適用します。WSL向け事前確認では、計画時にも専用XFSが必要です。通常ユーザーの計画ではrootでのKVM検査を保留した旨を表示し、rootの適用前に検査します。

    配置後はWSL内の通常ユーザーで実行します。

    oaiso runtime-check

    すべてokになった後、初回VM起動を確認します。WSLを再起動した後も、XFSのmountとoaiso runtime-checkを再確認してください。detachedワーカーの実行中もWSLのセッションを維持し、Windowsの休止・再起動による中断に備えて成果物を保存します。

    通信で失敗する場合¶

    • まずWSL自身のDNS・HTTPS・企業proxy/CAを確認します。NATとmirroredのどちらかをOaisoが自動選択することはありません。
    • WSL自身で名前解決できても、Proxyの別network namespaceから同じDNSへ届くとは限りません。Proxyだけが名前解決に失敗する場合は、管理者がoaiso node serve --helpの--proxy-dnsで到達可能な非loopback DNSを指定します。企業DNSの代わりに公開DNSへ自動切替することはありません。ノード設定を変更する前に作業を保存し、既存unitのmanifest・他の引数と更新後の設定も照合してください。
    • ip route show table allでVPNの経路を確認します。Oaisoは既存経路と重ならない10.253.x.0/24を選びます。全範囲が重なる場合は、ネットワーク管理者と経路を調整してください。
    • Windows/Hyper-V firewallとLinuxのforwarding規則を確認します。一括無効化やfirewall全消去で解決しないでください。
    • 認証Proxyの実資格情報はホスト側だけに置きます。Windowsのproxyへ接続するために、ワーカーのprivate-address制限を全解除する必要はありません。通信設定を使用します。
