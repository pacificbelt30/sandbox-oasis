    ドキュメントを追加・修正する¶

    日本語 | English

    • 対象：ドキュメントを修正する開発者。
    • Oaisoを使い始める手順：インストール・クイックスタート。
    • 編集時はSKILL.mdの共通ルールを守ります。

    内容と書き方を決める¶

    内容 書く場所・書き方
    製品の概要・導入・基本操作 README。変更履歴や新バージョンの告知は載せない
    リリースごとの変更点 doc/release-notes.md・GitHub Releases
    機能の使い方・制限 各機能の説明ページ。初収録版も記載する
    改善計画 本製品の要件・制限・完了条件で記載。他製品の名指し評価・順位・コード量比較は公開文書へ載せない
    比較・設定項目 表
    実行する順番 番号付き箇条書き
    条件・注意・補足 短い箇条書き。1項目に1つの内容を書く
    • 日本語は短く、具体的に書く。難解な言い回しを使わない。
    • 各機能に利用可能：v0.0.3以降などの初収録版を付ける。ページ内で導入版が違う場合も、機能ごとに示す。
    • 初収録版はタグ・履歴で確認する。手順を更新した版と、機能を追加した版を混同しない。
    • 未公開の機能は未リリース（main）と記載し、公開後に初収録版へ更新する。

    説明内容を確かめる¶

    観点 編集時の確認
    読者と順序 初回利用・既存環境の更新・開発作業を区別し、前提から後片付けまで案内する
    実装 help・設定例・コードを照合する。公開版とmainの機能を混同しない
    選択肢 既定・必須・任意を示す。必要な一経路を先に書く
    権限と影響 ホストとVM、通常ユーザーと管理者、共有ファイル、外部通信、削除範囲を区別する
    成功と失敗 終了コードと次の確認を示す。失敗時は直す場所と再確認コマンドを付ける
    根拠 コマンドの開始表示、保存、接続、推論、成果を区別する。fixture・skip・未実行を実機成功に数えない
    重複 詳細の置き場所を一つにし、関連する目次・リンク・日英・設定例をそろえる
    秘密 実APIキー・OAuth・認証ファイルを例やログに載せず、確認のために実推論を追加しない
    • 文書編集にはoaiso-docsを使う。その他の繰り返す作業はスキル一覧から選ぶ。

    新しいページを置く場所¶

    章 読者の目的 書く内容
    はじめに 最初に動かすには インストール・前提・認証・初回起動
    利用ガイド 目的の作業をするには エージェント・ファイル・イメージ・認証・通信・隔離
    リファレンス コマンドや設定を調べたい CLIの引数・設定項目・APIの指定方法
    管理・運用 配置後に維持するには 日常操作・ホスト更新・VM管理・移行・障害対応・性能
    開発 仕組みと検証方法は何か 構成・ネットワーク・上流追従・テスト・今後の対応

    読む順番に手順を書く¶

    1. 最初に「何ができる手順か」を書く。
    2. 必要なツール・公式の導入手順へのリンク・権限・実行するディレクトリを書く。
    3. コピーして実行できるコマンドを、番号付きの順番で並べる。
    4. 各操作の出力例と、どの表示なら次へ進めるかを書く。

    5. 失敗したときに確認する項目と、詳しい説明へのリンクを付ける。

    6. 選択肢・設定・制限は表で比較し、短い補足は箇条書きにする。

    7. 未実装の機能や、動作を確認していない条件は、そのまま明記する。
    8. 実際のAPIキー・ログイントークンを例へ載せない。
    9. 新しいページは、関連ガイドと mkdocs.yml の目次からリンクする。
    10. 日本語と英語で内容・配置をそろえる。未翻訳のページへのリンクには「日本語」と書く。
    11. パスや見出しを変えたら、そのページへのリンクも修正する。

    コマンドと出力例を書く¶

    項目 書き方
    コピーして実行するコマンド bash ブロック。入力記号 $ と出力を混ぜない
    人が読む出力 直後に text ブロック。正常時の目印と次の確認を添える
    JSON出力 json ブロック。整形・抜粋した場合は明記
    利用者や実行ごとに変わる値 版・ID・PID・時刻・パスなどが例であることを明記
    成功時に出力がない操作 「成功時は出力なし」と書き、確認コマンドを添える
    エラーの例 失敗箇所・修正の手掛かり・再確認の順で示す
    認証・起動の判定 保存成功・準備完了・実行中・タスク成功を区別
    複数コマンド 同じブロックを上からまとめて実行できる順序にする。実行ユーザー・作業場所・必要な置換を先に明記
    条件別・代替の手順 選ぶ条件を見出しに書き、コードブロックを分ける。コメントアウトした代替コマンドを混ぜない
    対話入力・シェル切り替え・再ログイン その前後でブロックを分け、続行する場所を示す
    • ローカルで試せる表示：一時的なHOMEと架空の認証情報でCLIを実行し、出力を比べる。
    • Kataが必要な表示：実装や既存のテスト記録と比べる。実機で試していない場合は、動作確認済みと書かない。
    • 長いビルドログ：先頭・末尾など必要な箇所だけを示し、省略範囲を明記。

    条件ごとにコードブロックを分ける例¶

    • 前提：実行ホストと選ぶエージェントの認証を準備済み。通常ユーザーで、作業プロジェクトのディレクトリから実行。
    • 以下はどちらか一方だけを選ぶ。各ブロックは上からまとめて実行できる。

    Codexを使う場合

    oaiso init --agent codex
oaiso codex --version

    Claude Codeを使う場合

    oaiso init --agent claude
oaiso claude --version

    公開前に確認する¶

    • 前提：uv。ホストの配置・CIと同じuv管理Python 3.12を使用。
    • 実行場所：リポジトリのルート。
    uv python install 3.12
uv run --no-project --no-config --managed-python --python 3.12 --with-requirements requirements-docs.txt mkdocs build --strict
    • コマンドの成功条件：終了コード 0 と、末尾の Documentation built in ... seconds。
    • 目次にページがあるか、ページ・見出しへのリンクが切れていないかを確認。
    • コマンド例は実装と照合。書式だけの検査と、実際に動かした確認を区別。
    • READMEにリリースの変更点・告知がなく、各機能の説明に正しい初収録版があるか確認。
    • コマンドの順序・変数・作業場所を確認し、条件別の代替や対話入力を同じブロックに混ぜていないか確認。
    • CLI一覧・フラグ表：通常サブコマンドの --help と照合。codex / claude の --help はエージェント側に渡るため別扱い。
    • 設定名・値の形式・適用先・優先順位を日英で確認。利用者設定とプロジェクト設定では、起動コマンドの書式も異なる。
    • 認証・更新の手順は、準備から確認まで順にたどる。ドキュメントのビルド成功と、製品の動作確認は分けて記録する。
