# 計測して高速化する

## 測定を組み立てる

1. [性能ガイド](../../../doc/performance.md)で既存の計測対象・工程・benchmarkを確認する。
2. 何を速くするか決め、変更前のコマンド、commit、Go版、CPU条件、イメージ、資源プロファイル、キャッシュ条件を記録する。
3. 総時間を工程別に分け、時間を使っている箇所を特定する。必要な箇所だけCPU・メモリのprofileを取得する。
4. 複雑化を伴う候補は、20%以上の改善が見込める根拠を示して優先する。見込みと実測の改善率は区別する。

## Proxy認証を測る例

リポジトリのルートで実行する。Kata・実API・実資格情報は不要。

```bash
go test ./internal/authproxy -run '^$' \
  -bench '^BenchmarkWorkerRequest$' -benchmem -count=5 -benchtime=500ms
```

- 資産検証・実Kata Exec・起動時間の計測は[対象ごとのコマンド](../../../doc/performance.md#再計測する)を使う。実Kataは検証専用ノードを選ぶ。
- benchmarkがskipした場合は測定成功とみなさない。

## 変更前後を比較する

| 観点 | 条件 |
|---|---|
| 比較 | 同じGo・CPU条件・固定資産・プロファイル。測定中は競合するビルドや試験を止める |
| 標本 | 複数回測り、旧版・新版の順序も入れ替える。中央値とばらつきを確認 |
| 初回と再利用 | cold／warm、イメージ取得／起動、解錠／解錠後の処理を分ける |
| 範囲 | 単体benchmark、起動全体、実タスク、AI応答時間を混同しない |
| 費用 | 時間だけでなくメモリ、CPU、割当て、補充・検証の費用も確認 |

- 資産の再検証、bootstrap gate、認証、通信制限、UID、権限、資源上限、所有権確認を省いて速くしない。
- 測定結果は`.kata-verification/`へ保存し、再現コマンドと要約だけを文書へ記載する。プロファイルやログに秘密を残さない。
- 実装後は[変更後のテスト](../oaiso-test/SKILL.md)を行い、実行経路の変更なら[実Kata検証](../oaiso-kata-test/SKILL.md)も行う。
- 条件・変更前後の値・改善率・増えた費用・未確認範囲を報告する。単体の改善率を製品全体の改善率に置き換えない。
