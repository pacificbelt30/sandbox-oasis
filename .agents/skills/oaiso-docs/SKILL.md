# ドキュメントを編集する

## 最初に読む

- [共通の編集ルール](../../../SKILL.md#ドキュメント編集)を守る。
- [日英の編集ガイド](../../../doc/development/documentation.md)で置き場所・表記・確認方法を調べる。

## 編集する

1. 読者の目的と対象版を決め、初回利用・既存環境の更新・開発作業のどれかを明確にする。
2. 実装、通常サブコマンドの`--help`、設定例、既存の試験記録を照合する。`oaiso codex/claude --help`はエージェント側へ渡るため、製品のフラグ確認には使わない。
3. 機能の初収録版をタグ・履歴で確認する。未公開なら`未リリース（main）`と書く。
4. 一つの実行経路を先に示し、必要な条件・権限・作業場所・副作用・成功条件を付ける。代替手順は別ブロックへ分ける。
5. 機能の詳しい説明は一か所で管理し、READMEなどの要約からリンクする。日英・目次・設定例・関連ページの内容をそろえる。
6. 出力例と実行結果を区別する。基盤準備・保存・接続・推論・タスク成功を一括で「動作確認済み」にしない。

## 確認する

リポジトリのルートで実行する。uvと管理Python 3.12は[開発ツール](../../../doc/development/toolchain.md)に従って準備する。

```bash
uv run --no-project --no-config --managed-python --python 3.12 \
  --with-requirements requirements-docs.txt mkdocs build --strict
git diff --check
```

- strictビルドはリンク・構成の検査。コマンドの実動作を保証する検査ではない。
- 例の実行には一時HOME・架空の資格情報を使う。利用者の資格情報を読む操作や実API推論を、文書確認のために追加しない。
- Kataが必要な例は既存の証跡と照合する。新たに実機確認が必要な場合は[実Kata検証](../oaiso-kata-test/SKILL.md)へ進む。
- 変更内容と、実施した確認・未確認の範囲を短く報告する。文書だけの変更にGo全件テストを追加しない。
